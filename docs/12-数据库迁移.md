## 12.1 ORM 选型

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **Prisma 6.19.3（采用）** | ✅ 主方案 | 类型安全客户端、与 Nest DI 易集成、`prisma generate` 在交付机成功（引擎二进制下载正常）；schema 可作为契约 §2 的可校验镜像 |
| Drizzle ORM | 备选 | 纯 TS、无引擎二进制，但需要自行维护更细的 SQL 构建器；仅在 Prisma 引擎下载失败时启用 |
| node-postgres + 手写 SQL | 兜底 | 零代码生成、完全可控；但 18 张表的类型与查询要手写，开发成本最高 |

实际执行记录：

```text
pnpm prisma:validate   → Prisma schema loaded from prisma\schema.prisma（通过）
pnpm prisma:generate   → ✔ Generated Prisma Client (v6.19.3)
```

因此**未触发降级**，Drizzle / pg 方案仅作为文档留档。

### 为什么迁移 SQL 手写而不是 `prisma migrate dev`

契约 §2 要求以下特性，Prisma schema 无法完整表达，只能落到 SQL：

1. **部分唯一索引**：`UNIQUE(user_id, emoji, message_id) WHERE message_id IS NOT NULL`（reactions / attachments 各两条）。
2. **生成列**：`messages.search_vector tsvector GENERATED ALWAYS AS (to_tsvector('simple', coalesce(body,''))) STORED`。
3. **GIN + pg_trgm 操作符类**：`GIN(body gin_trgm_ops)`。
4. **inet 列**：Prisma 无对应原生类型（schema 中标记 `Unsupported("inet")`，写入走原生 SQL）。
5. **CHECK 约束**：`num_nonnulls(message_id, card_id) = 1`、`handle` 正则、`body` 长度、投票色标枚举等。

所以采用 **“Prisma schema 管类型 + 手写 SQL 管真库”** 的分工：`schema.prisma` 只做客户端类型来源（`prisma generate`），DDL 以 `0001_init/migration.sql` 为准，执行走 `prisma migrate deploy`（它只记录 `_prisma_migrations` 并执行目录内 SQL，不做 diff）。

## 12.3 关键 SQL 摘录

### 12.3.1 幂等唯一键（契约 §2.8 / §6）

```sql
CREATE UNIQUE INDEX messages_channel_sender_client_key
  ON messages (channel_id, sender_id, client_msg_id);
```

服务端发消息时先尝试 `INSERT`；命中该索引即返回已存消息并 `dup:true`，不再重复落库。

### 12.3.2 搜索生成列 + 双索引（契约 §2.8）

```sql
search_vector tsvector GENERATED ALWAYS AS (
  to_tsvector('simple'::regconfig, coalesce(body, ''::text))
) STORED;

CREATE INDEX messages_search_vector_idx ON messages USING GIN (search_vector);
CREATE INDEX messages_body_trgm_idx    ON messages USING GIN (body gin_trgm_ops);
```

`simple` 配置对中文不分词，故同时保留 `pg_trgm` 子串索引作为中文兜底（搜索实现见 `search.service.ts`）。

### 12.3.3 部分唯一索引（契约 §2.9 / §2.11）

```sql
CREATE UNIQUE INDEX reactions_user_emoji_message_key
  ON reactions (user_id, emoji, message_id) WHERE message_id IS NOT NULL;
CREATE UNIQUE INDEX reactions_user_emoji_card_key
  ON reactions (user_id, emoji, card_id)    WHERE card_id    IS NOT NULL;

CREATE UNIQUE INDEX attachments_file_message_key
  ON attachments (file_id, message_id) WHERE message_id IS NOT NULL;
CREATE UNIQUE INDEX attachments_file_card_key
  ON attachments (file_id, card_id)    WHERE card_id    IS NOT NULL;
```

### 12.3.4 邀请原子扣减（契约 §5）

Prisma 生成的实际语句（事务内，单条即可保证并发安全）：

```sql
UPDATE invites
   SET uses = uses + 1
 WHERE id = $1
   AND revoked_at IS NULL
   AND expires_at > now()
   AND uses < max_uses;
-- affectedRows = 0 → INVITE_INVALID（不区分不存在/过期/用尽，契约 §5）
```

### 12.3.5 已读游标单调推进（契约 §3）

```sql
UPDATE channel_members
   SET last_read_seq = $1, last_read_at = now()
 WHERE channel_id = $2 AND user_id = $3 AND last_read_seq < $1;
```

由 300ms 合并器批量调用（`common/realtime/read-receipt.service.ts`），`WHERE last_read_seq < $1` 保证不会回退。

### 12.3.6 循环外键

```sql
ALTER TABLE users  ADD CONSTRAINT users_avatar_file_id_fkey
  FOREIGN KEY (avatar_file_id) REFERENCES files(id) ON DELETE SET NULL;
ALTER TABLE messages ADD CONSTRAINT messages_card_id_fkey
  FOREIGN KEY (card_id) REFERENCES cards(id) ON DELETE SET NULL;
ALTER TABLE cards ADD CONSTRAINT cards_message_id_fkey
  FOREIGN KEY (message_id) REFERENCES messages(id) ON DELETE SET NULL;
```

### 12.3.7 线程形状约束

```sql
CONSTRAINT messages_thread_shape CHECK (
  (parent_id IS NULL AND thread_root_id IS NULL)
  OR (parent_id IS NOT NULL AND thread_root_id IS NOT NULL)
);
```

单层线程由应用层保证：`parent_id` 必为根，`thread_root_id` 恒等于根 id（`messages.service.ts#insertMessage`）。

### 12.3.8 会话扩展（契约 v1.2 §A，`0002_conversations`）

```sql
CREATE TYPE "ChannelKind" AS ENUM ('channel', 'dm', 'group');

ALTER TABLE channels ADD COLUMN kind "ChannelKind" NOT NULL DEFAULT 'channel';
ALTER TABLE channels ADD COLUMN dm_key varchar(80) NULL;
ALTER TABLE channels ADD COLUMN last_message_at timestamptz NULL;

-- 同一对人永远只有一行；普通频道 / 群聊 dm_key 为 NULL，不参与唯一性
CREATE UNIQUE INDEX channels_dm_key_key ON channels (dm_key) WHERE dm_key IS NOT NULL;
CREATE INDEX channels_kind_position_idx ON channels (kind, position);

ALTER TABLE channels ADD CONSTRAINT channels_dm_key_kind_check CHECK (dm_key IS NULL OR kind = 'dm');
ALTER TABLE channels ADD CONSTRAINT channels_group_name_check CHECK (
  kind <> 'group' OR char_length(btrim(name)) BETWEEN 1 AND 60
);
```

要点：

- **不新建 conversations 表**：DM / 群聊复用 `channels` + `channel_members`，消息 / 已读 / 线程 / 附件 / 反应链路零重复（契约 v1.2 §A1）。
- 存量频道行因 `DEFAULT 'channel'` 全部落回社区语义，`GET /channels` 也只查 `kind='channel'`，社区行为不变。
- `dm_key` = `sha256(排序后的两个 userId 以 ':' 连接)`（64 位小写十六进制），插入冲突即读回已有会话（`PrismaService.isUniqueViolation`）。
- 部分唯一索引 `WHERE dm_key IS NOT NULL` 是 DM 幂等的最终保证；应用层先查后建，并发时由该索引兜底。
- `last_message_at` 由 `messages.service#insertMessage` 与消息插入**同一事务**更新，供 `GET /conversations` 按 `last_message_at desc nulls last` 排序。
- 一方退出 DM 时清空 `dm_key`（会话行与历史保留），因此 CHECK 只要求「`dm_key` 只能出现在 kind=dm 上」，允许 DM 行 `dm_key IS NULL`。
- 本文件**不写显式 `BEGIN/COMMIT`**：`prisma migrate deploy` 对 PostgreSQL 会把每个迁移文件包在事务里执行；0001 的显式事务属历史写法（两者并存只会产生嵌套告警）。

### 12.3.9 Sprint1（v1.2 Sprint1，`0003_v2_sprint1`）

```sql
ALTER TABLE users ADD COLUMN status_prefix varchar(24) NULL;

ALTER TABLE channels ADD COLUMN announcement text NULL;

-- 公告只允许出现在群聊；长度与 DTO 校验一致
ALTER TABLE channels ADD CONSTRAINT channels_announcement_kind_check CHECK (
  announcement IS NULL OR kind = 'group'
);
ALTER TABLE channels ADD CONSTRAINT channels_announcement_length_check CHECK (
  announcement IS NULL OR char_length(announcement) <= 4000
);
ALTER TABLE users ADD CONSTRAINT users_status_prefix_length_check CHECK (
  status_prefix IS NULL OR char_length(status_prefix) <= 24
);
```

要点：

- **只做加法**：两列均可空，存量行无需回填；`status_prefix` 为 `varchar(24)`，`announcement` 为 `text`（与 `schema.prisma` 的 `@db.VarChar(24)` / `@db.Text` 一致）。
- 两条 CHECK 是“实现侧加固”：公告只允许挂在 `kind='group'` 上（DM/频道写公告在应用层已被 `CONVERSATION_KIND_INVALID` 拒绝，DB 再兜一层），长度上限与 DTO 的 `max(24)` / `max(4000)` 对齐。
- 解散群聊**不新增列**：复用 `channels.archived_at`，`DELETE /conversations/:id` 在 `Prisma.$transaction` 内只置 `archived_at=now()`；消息、`channel_members` 原样保留（软归档），列表/详情按 `archived_at IS NULL` 过滤。
- 本机已在 embedded PG 17.5（`127.0.0.1:55432/dijiang`）通过 `prisma migrate deploy` 应用，`_prisma_migrations` 记录 `0003_v2_sprint1` 完成于 `2026-10-23T15:32:50.494Z`；`information_schema.columns` 实测：`users.status_prefix varchar(24)`、`channels.announcement text`。

### 12.3.10 Sprint2（`0004_sprint2`：music/chart 卡片 + 贴纸）

```sql
-- CardKind 追加两种卡片类型（PG12+ 允许在事务内 ADD VALUE，只要本事务不使用新值）
ALTER TYPE "CardKind" ADD VALUE IF NOT EXISTS 'music';
ALTER TYPE "CardKind" ADD VALUE IF NOT EXISTS 'chart';

CREATE TABLE stickers (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id   uuid        NOT NULL,
  file_id    uuid        NOT NULL REFERENCES files (id) ON DELETE CASCADE,
  name       varchar(40) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT stickers_owner_file_key UNIQUE (owner_id, file_id)
);
CREATE INDEX stickers_owner_id_idx ON stickers (owner_id);
CREATE INDEX stickers_owner_created_idx ON stickers (owner_id, created_at DESC);
```

要点：

- **枚举扩展只增不改**：`music` / `chart` 追加在 `material/idea/vote/task/artwork` 之后；`schema.prisma`、`server/src/common/types/enums.ts` 的 `CARD_KINDS` 与 `POST /cards` 的 zod 枚举同步扩到 7 种，存量数据与 API 行为不变。
- `ALTER TYPE ... ADD VALUE` 在 PG12+ 可放在 `prisma migrate deploy` 的事务块里（本迁移没有在同一个事务里写入这两个新枚举值，符合限制）；因此 0004 与 0002/0003 一样不写显式 `BEGIN/COMMIT`。
- `stickers` 是**个人**贴纸库：唯一键 `(owner_id, file_id)` 保证“同一文件只收藏一次”，应用层命中 `P2002` 时幂等返回已有行；`file_id` 外键 `ON DELETE CASCADE`，文件清理时贴纸一起回收。
- 索引 `(owner_id)` 用于按用户取贴纸；`(owner_id, created_at DESC)` 直接支撑 `GET /stickers` 的 `createdAt desc` 排序。
- 本机实测：`_prisma_migrations` 记录 `0004_sprint2` 完成于 `2026-10-24T03:47:17.948Z`；`pg_enum` 实测 `CardKind` 7 个值（含 `music`/`chart`）；`information_schema.columns` 实测 `stickers.name = character varying(40)` 等 5 列。
- 回滚：`DROP TABLE stickers` 可回退表；但 PostgreSQL **不支持 `DROP VALUE`**，若要回退枚举值需重建 `CardKind` 类型（业务已写入 music/chart 时须先迁移数据）。

### 12.3.11 Sprint3（`0005_sprint3`：AI 配置 + 固定 bot 用户）

```sql
ALTER TABLE users ADD COLUMN is_bot boolean NOT NULL DEFAULT false;

-- 固定 bot 用户：UUID 与 server/src/ai/bot.constants.ts 的 BOT_USER_ID 一致
INSERT INTO users (id, handle, display_name, password_hash, global_role, status, is_bot)
VALUES ('00000000-0000-4000-8000-0000000000b0', 'dijiang_bot', '帝江号·协议官', '!bot', 'member', 'active', true)
ON CONFLICT DO NOTHING;

CREATE TABLE ai_settings (
  id                text        PRIMARY KEY DEFAULT 'default',
  base_url          text        NULL,
  model             text        NULL,
  api_key_encrypted text        NULL,
  updated_by        uuid        NULL REFERENCES users (id) ON DELETE SET NULL,
  updated_at        timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ai_settings_singleton_check CHECK (id = 'default')
);
```

要点：

- **固定 bot 身份**：`users.is_bot=true` 标记系统账号；`dijiang_bot` 的 `password_hash='!bot'` 是永远无法通过 argon2 校验的占位串，该账号不可登录；`ON CONFLICT DO NOTHING` 让迁移可安全重放。
- **AI Key 加密**：`ai_settings.api_key_encrypted` 只存 `v1:<ivB64>:<tagB64>:<cipherB64>`（AES-256-GCM，密钥由 `AI_CONFIG_SECRET` 经 SHA-256 派生）；任何 GET/日志/错误都不返回明文（见 `AiConfigService.adminGet` 的 `keyMasked`）。
- **单行约束**：`CHECK (id = 'default')` + 主键固定值，保证配置表只有一行；`updated_by` 外键 `ON DELETE SET NULL`，删除管理员账号不会级联删配置。
- 本机实测：`_prisma_migrations` 记录 `0005_sprint3` 完成于 `2026-10-24T04:10:48.455Z`；`users` 中 bot 行 `id=00000000-0000-4000-8000-0000000000b0 / handle=dijiang_bot / is_bot=true / password_hash=!bot`；`ai_settings` 6 列与 CHECK 均随迁移创建。
- 回滚：`DROP TABLE ai_settings` + 删除 bot 行/`is_bot` 列；注意 bot 消息的 `sender_id` 外键，生产回退前需先处理历史消息。

### 12.3.12 Sprint4（`0006_sprint4`：朋友圈 posts / likes / comments）

```sql
CREATE TABLE posts (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  author_id  uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  body       text        NOT NULL,
  file_ids   jsonb       NOT NULL DEFAULT '[]'::jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz NULL,
  CONSTRAINT posts_body_length_check CHECK (char_length(body) BETWEEN 1 AND 4000)
);
CREATE INDEX posts_created_at_idx ON posts (created_at DESC);
CREATE INDEX posts_author_id_idx ON posts (author_id, created_at DESC);

CREATE TABLE post_likes (
  post_id    uuid        NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
  user_id    uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (post_id, user_id)
);
CREATE INDEX post_likes_user_id_idx ON post_likes (user_id);

CREATE TABLE post_comments (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id    uuid        NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
  author_id  uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  body       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT post_comments_body_length_check CHECK (char_length(body) BETWEEN 1 AND 2000)
);
CREATE INDEX post_comments_post_created_idx ON post_comments (post_id, created_at);
```

要点：

- **软删**：`DELETE /posts/:id` 只置 `deleted_at`（作者本人 + Prisma 事务），列表/点赞/评论均过滤 `deleted_at IS NULL`；消息/评论/点赞数据不物理删除。
- **点赞幂等**：`PRIMARY KEY (post_id, user_id)` 是最终保证；应用层 `createMany({ skipDuplicates: true })`，重复点赞不报错、计数不变。
- `file_ids` 为 `jsonb` 数组（≤9 个 uuid，由 DTO 限制）；不用附件表是因为朋友圈图片是“展示引用”，不参与消息/卡片附件链路。
- 索引：`posts(created_at DESC)` 支撑倒序分页；`posts(author_id, created_at DESC)` 支撑作者维度；`post_comments(post_id, created_at)` 支撑评论正序；`post_likes(user_id)` 支撑“我赞过的”。
- 本机实测：`_prisma_migrations` 记录 `0006_sprint4` 完成于 `2026-10-24T04:24:48.968Z`；`posts` / `post_likes` / `post_comments` 三表与 `posts_created_at_idx`、`posts_author_id_idx`、`post_likes_user_id_idx`、`post_comments_post_created_idx` 均随迁移创建。
- 回滚：`DROP TABLE post_comments, post_likes, posts;`（先删子表）。

### 12.3.13 多 Bot（`0007_bots`：bot_profiles + ai_channel_contexts）

```sql
CREATE TABLE bot_profiles (
  user_id           uuid        PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
  system_prompt     text        NOT NULL DEFAULT '',
  model             varchar(80) NULL,
  api_key_encrypted text        NULL,
  enabled           boolean     NOT NULL DEFAULT true,
  created_by        uuid        NOT NULL REFERENCES users (id),
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  deleted_at        timestamptz NULL
);
CREATE INDEX bot_profiles_created_by_idx ON bot_profiles (created_by);
CREATE INDEX bot_profiles_deleted_at_idx ON bot_profiles (deleted_at);

CREATE TABLE ai_channel_contexts (
  channel_id uuid        NOT NULL REFERENCES channels (id) ON DELETE CASCADE,
  bot_id     uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  cleared_at timestamptz NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (channel_id, bot_id)
);

-- 默认 Bot（dijiang_bot）建 profile：人设=协议官；model/key 为空表示回退全局 ai_settings
INSERT INTO bot_profiles (user_id, system_prompt, enabled, created_by)
SELECT u.id, '你是「帝江号·协议官」…', true, u.id
FROM users u WHERE u.id = '00000000-0000-4000-8000-0000000000b0'
ON CONFLICT (user_id) DO NOTHING;

-- 默认 Bot 加入所有未归档频道（可重放）
INSERT INTO channel_members (channel_id, user_id, role)
SELECT c.id, '00000000-0000-4000-8000-0000000000b0', 'member'
FROM channels c WHERE c.archived_at IS NULL
ON CONFLICT (channel_id, user_id) DO NOTHING;
```

要点：

- **复用 users 表**：Bot 不是独立主体，而是 `users(is_bot=true)` 的一行；`bot_profiles.user_id` 既是主键又是外键，删除 Bot 时 profile 级联删除，但 `DELETE /bots/:id` 走的是**软删**（`deleted_at` + `user.status=suspended`），历史消息的 `sender_id` 仍有效。
- **Key 加密**：`bot_profiles.api_key_encrypted` 与全局 `ai_settings` 共用 `AI_CONFIG_SECRET` 的 AES-256-GCM；Bot 无自己的 key/model 时回退全局配置。
- **上下文水位**：`POST /ai/clear` 只写 `ai_channel_contexts.cleared_at`，聊天记录不删；`/ai/chat` 按 `cleared_at` 过滤历史（summarize 按最近 50 条，不按水位）。
- **频道成员关系**：Bot 是否能被 @ 由 `channel_members` 决定（复用现有加成员接口，`upsert` 天然防重复）；`enabled=false` 或 `user.status=suspended` 时返回 `BOT_DISABLED`。
- 本机实测：`_prisma_migrations` 记录 `0007_bots` 完成于 `2026-10-24T05:01:20.398Z`；`bot_profiles` / `ai_channel_contexts` 两表创建；默认 Bot profile `enabled=true`、`prompt_len=90`、`model=NULL`/无 key（回退全局）；默认 Bot 已加入 8 个未归档频道。
- 回滚：`DROP TABLE ai_channel_contexts; DROP TABLE bot_profiles;`（先删引用表）。

### 12.3.14 Phase3（`0008_phase3`：全服公告单行表）

```sql
CREATE TABLE system_announcements (
  id         text        PRIMARY KEY DEFAULT 'default',
  body       text        NOT NULL,
  level      varchar(16) NOT NULL DEFAULT 'info',
  active     boolean     NOT NULL DEFAULT true,
  updated_by uuid        NULL REFERENCES users (id) ON DELETE SET NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT system_announcements_singleton_check CHECK (id = 'default'),
  CONSTRAINT system_announcements_body_length_check CHECK (char_length(body) BETWEEN 1 AND 2000),
  CONSTRAINT system_announcements_level_check CHECK (level IN ('info', 'warning', 'critical'))
);
```

要点：

- **单行表**：`id='default'` CHECK + 主键，保证只有一条公告；`PUT /announcements` 用 `INSERT ... ON CONFLICT (id) DO UPDATE`。
- **关闭不删**：空 body 只把 `active=false`，保留 body（因此 `body` 始终满足 1..2000）；`GET /announcements/current` 只看 `active=true`，关闭后返回 `announcement:null`。
- `updated_by` 外键 `ON DELETE SET NULL`（删管理员不级联删公告）；`level` 仅 `info/warning/critical`，与 DTO 一致。
- 写入路径在 `AnnouncementsService` 用参数化 `$executeRaw`/`$queryRaw`（为在“API 不重启交付”期间可先应用迁移；`schema.prisma` 同时已加 `SystemAnnouncement` 模型，下次 `prisma generate` 后可直接用 client）。
- 本机实测：`prisma migrate deploy` 已应用 `0008_phase3`；`information_schema` 实测 6 列：`id/body/level/active/updated_by/updated_at`。
- 回滚：`DROP TABLE system_announcements;`。

## 12.5 迁移策略（expand / contract）

MVP 单租户、表量小，仍按 expand/contract 三段式约束后续变更：

1. **expand（可回滚窗口）**：只做加法——新增可空列 / 新表 / 新索引（`CREATE INDEX CONCURRENTLY` 走单独迁移文件，因为不能在事务块内）。
2. **migrate（双写/回填）**：应用同时读写新旧结构；回填用批量 `UPDATE ... WHERE ... LIMIT`，避免长事务锁表。
3. **contract（收口）**：确认无旧代码引用后，删除旧列 / 旧索引 / 临时双写逻辑。

约定：

- 迁移文件命名 `NNNN_name/migration.sql`，**只追加不修改**；发现错误用新迁移修正。
- 每个迁移单独 PR，附 `prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --script` 的候选输出作为 review 参考（本仓库用手写 SQL，diff 只做校验）。
- 上线顺序：先 expand 迁移 → 再滚动发布应用 → 最后 contract 迁移。
- 禁止在迁移里写业务数据修复，数据修复走 `scripts/` 一次性脚本并留审计。

## 12.6 回滚方案

`prisma migrate deploy` 不自动生成 down 脚本。回滚按“整库重建 / 单迁移手工回滚”两档处理：

### A. 本地/单机（数据可丢）

```bash
# 停止应用后
docker compose -f ops/docker-compose.yml down -v          # 删除数据卷
docker compose -f ops/docker-compose.yml up -d postgres redis minio
make -C ops migrate init-owner seed                       # 重放 0001_init + 种子
```

### B. 生产（需保留数据）

1. 记录当前迁移点：`prisma migrate status`。
2. 将失败迁移标记为已回滚：`prisma migrate resolve --rolled-back 0001_init`。
3. 手工执行对应的 down SQL（0001 的 down 如下，**执行前必须备份**）：

```sql
BEGIN;
-- 按依赖反向删除（CASCADE 处理外键）
DROP TABLE IF EXISTS audit_logs, notifications, vote_ballots, vote_options,
  card_assignees, pins, attachments, cards, reactions, messages,
  files, channel_members, channels, invites, sessions, devices,
  user_settings, users CASCADE;
-- 枚举类型
DROP TYPE IF EXISTS "Platform", "PushStatus", "NotificationType", "PreviewStatus",
  "FileStatus", "FileKind", "TaskStatus", "CardStatus", "CardKind",
  "MessageKind", "NotifyLevel", "Visibility", "ChannelRole", "UserStatus",
  "GlobalRole" CASCADE;
-- 扩展按环境策略保留（可能被其他库共享）
COMMIT;
```

4. 恢复备份或重跑修正后的迁移。
5. 迁移失败且事务未提交时（本迁移是单事务），PG 会自动回滚，无需手工清理。

## 12.7 与契约的已知偏差 / 实现取舍

| 项 | 契约要求 | 实际实现 | 影响 |
| --- | --- | --- | --- |
| 上传大小约束 | §10 “签名含 `content-length-range`” | 预签名 **PUT** 不支持 policy 条件；改为 `complete` 阶段 `HeadObject` 严格比对 `size_bytes`，不一致删除对象并置 `rejected` | 大小校验延后到 complete，仍能拒绝超限对象 |
| 预签名 host | §10 返回 `uploadUrl` | **双 S3Client**：数据面（HEAD/GET/DELETE）用 `S3_ENDPOINT`（容器内网），签名面（presignPut/presignGet）用 `S3_PUBLIC_ENDPOINT`（浏览器可达）；单测断言签名 URL 的 host 是公网端点而非 `minio:9000` | `S3_PUBLIC_ENDPOINT` 不能带路径前缀（SigV4 会签 path），只能用独立端口/子域；Caddy 已移除 `/files/*` 反代 |
