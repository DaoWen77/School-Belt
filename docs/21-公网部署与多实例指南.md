## 21.1 拓扑

### 21.1.1 同源单机（Caddy 推荐）

```text
                    HTTPS/WSS
浏览器 ──────────────────────────────► Caddy (:443)
                                          │
                    ┌─────────────────────┼──────────────────────┐
                    │ /api/*              │ /socket.io/*         │ 其余
                    ▼                     ▼                      ▼
              API 实例 :3000        API 实例 :3000          Next.js :3100
                    │                     │
                    └────────┬────────────┘
                             ▼
                 Redis（必需：限流/在线/WS adapter）
                 PostgreSQL（DATABASE_POOL_MAX/实例）
                 S3 / MinIO（独立公网端点，SigV4）

files.example.com ──HTTPS──► MinIO/S3 :9000（独立端口/子域，不经 Caddy /files 前缀）
```

- 前端与 REST/WS **同源**：CORS 只需 `https://dijiang.example.com`，无 Cookie（Bearer token），不存在 SameSite 问题。
- 静态资源/SSR 由 Next.js 提供；Caddy/nginx 只做 TLS 终止与路由。
- S3 必须是**浏览器可直接访问的独立地址**（`S3_PUBLIC_ENDPOINT`），原因见 §21.8.4。

### 21.1.2 多实例（水平扩展）

```text
             ┌─────────────┐
浏览器 ─────►│ Caddy/nginx │──┬──► api-1 ─┐
             └─────────────┘  ├──► api-2 ─┼──► PostgreSQL
                              └──► api-N ─┘
                                   │
                                   └──► Redis（pub/sub：Socket.IO adapter）
```

- API 无状态（JWT + DB 会话），可多副本；广播由 `@socket.io/redis-adapter` 跨实例 fan-out。
- Redis 是**必需依赖**（启动 PING 失败即拒绝启动，不存在内存降级）。
- 每个 API 实例各建 `DATABASE_POOL_MAX` 个 PG 连接；`实例数 × 20` 必须小于 PG `max_connections`。
- 文件上传走浏览器→S3 预签名直传，不经过 API 实例，带宽不随 API 副本线性增长。

## 21.2 前置条件

| 项 | 要求 |
| --- | --- |
| 域名 | 一个 A/AAAA 记录指向服务器（或 Cloudflare 代理）；本文以 `dijiang.example.com` 为例 |
| 证书 | Caddy 自动 ACME / nginx + certbot / Cloudflare 边缘证书 |
| 端口 | 公网仅开 80/443；**不要**直接暴露 3000/3100/5432/6379/9000/9001 |
| 服务器 | Linux（Debian/Ubuntu 建议）；2C4G 起步；Node 22+ |
| 依赖 | PostgreSQL 16、Redis 7（必需）、S3/MinIO（独立公网地址）、Next.js 生产构建 |
| 构建 | `server`：`pnpm build`；`web`：`pnpm build`（`NEXT_PUBLIC_API_BASE_URL` / `NEXT_PUBLIC_WS_URL` 构建期注入） |

## 21.3 环境变量（公网同源）

### 21.3.1 后端（`server/.env` 或编排 env）

| 变量 | 公网取值 | 说明 |
| --- | --- | --- |
| `NODE_ENV` | `production` | 生产会拒绝默认 JWT 密钥与 RTC 开关 |
| `HOST` / `PORT` | `0.0.0.0` / `3000` | 仅容器/内网监听，公网由反代暴露 |
| `TRUST_PROXY` | `true` | 反代后必须开，否则限流/审计拿到的是反代 IP |
| `CORS_ORIGINS` | `https://dijiang.example.com` | 同源部署只需这一个；多个前端用逗号分隔 |
| `DATABASE_URL` | `postgresql://…@postgres:5432/dijiang` | 含 `connection_limit` 时以 URL 为准 |
| `DATABASE_POOL_MAX` | `20` | 每实例连接池；由 run-backend/Prisma 注入 `connection_limit` |
| `REDIS_URL` | `redis://:密码@redis:6379/0` | **必填**（无内存降级） |
| `REDIS_KEY_PREFIX` | `dijiang:prod:` | 多环境共用 Redis 时隔离 |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | 32+ 位随机串 | 不得以 `dev-` 开头 |
| `S3_ENDPOINT` | `http://minio:9000` | 服务端内部访问（容器 DNS） |
| `S3_PUBLIC_ENDPOINT` | `https://files.example.com` | 浏览器直传/下载；**独立端口或子域，不能带 `/files` 前缀** |
| `S3_BUCKET` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | 按对象存储填写 | MinIO 桶需配 CORS（预检/Origin） |
| `AI_CONFIG_SECRET` | 32+ 位随机串 | AI/Bot API Key 的 AES-256-GCM 加密密钥；生产必须覆盖默认值 |
| `PUSH_ENABLED` | `false`（未接凭据时） | 推送凭据齐全后再开 |
| `RTC_SIGNALING_ENABLED` | `false` | 契约预留，v1 必须 false |

### 21.3.2 前端（构建期变量）

| 变量 | 取值 | 说明 |
| --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | `https://dijiang.example.com` | REST 基地址；同源部署可留空（fallback `window.location.origin`） |
| `NEXT_PUBLIC_WS_URL` | `https://dijiang.example.com` | WS 基地址（可空=沿用 API host）；Socket.IO path 仍 `/socket.io`，命名空间 `/ws` |
| `NEXT_PUBLIC_WS_PATH` | `/socket.io` | 默认值即可 |
| 旧 `NEXT_PUBLIC_API_BASE` | `https://dijiang.example.com` | 兼容保留；新部署请用 `..._URL` |

> 优先级：登录页保存的服务器地址（`localStorage: dj-server-api` / `dj-server-ws`）→ 上述环境变量 → `window.location.origin`。
> 登录页可折叠「服务器设置」测试 `/readyz` 后保存；适合单前端连多个自托管实例。
> `NEXT_PUBLIC_*` 在 `next build` 时内联；改了必须重新 build，不能只重启进程。

## 21.4 Caddy 部署（推荐：自动 HTTPS）

### 21.4.1 准备

```bash
# 服务器上：安装 Caddy（官方 apt 源或单二进制）
# 目录约定（示例）
/opt/dijiang/
├── ops/Caddyfile
├── server/                 # 构建产物 + .env
└── web/                    # next build 产物
```

`ops/Caddyfile` 的环境变量：

| 变量 | 示例 | 说明 |
| --- | --- | --- |
| `DOMAIN` | `dijiang.example.com` | Caddy 站点域名；需解析到本机 |
| `ACME_EMAIL` | `ops@example.com` | Let's Encrypt 到期通知 |
| `WEB_UPSTREAM` | `web:3100` | Next.js 上游；裸机可用 `127.0.0.1:3100` |

本机无公网时改用自签：注释 `email` 行，并在站点块内加 `tls internal`，浏览器需手动信任证书。

### 21.4.3 Caddy 关键配置（节选，完整见 `ops/Caddyfile`）

```caddyfile
{$DOMAIN:localhost} {
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' ws: wss:; frame-ancestors 'none'"
        Permissions-Policy "camera=(), microphone=(), geolocation=(), payment=(), usb=()"
    }

    handle /api/* {
        reverse_proxy api:3000 {
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-Proto {scheme}
            header_up X-Forwarded-Host {host}
            flush_interval -1              # SSE 不缓冲
            transport http { read_timeout 3600s write_timeout 3600s }
        }
    }

    handle /socket.io/* {
        reverse_proxy api:3000 { flush_interval -1 }
    }

    handle { reverse_proxy web:3100 }      # Next.js
}
```

Caddy 自动处理 WS `Upgrade/Connection`；`X-Forwarded-For` 默认追加，无需手写。

## 21.5 nginx 部署

完整样例见 [ops/nginx.conf](../ops/nginx.conf)。关键片段：

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl; http2 on;
    server_name dijiang.example.com;
    ssl_certificate     /etc/letsencrypt/live/dijiang.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dijiang.example.com/privkey.pem;

    location /api/ {
        proxy_pass http://dijiang_api;
        proxy_http_version 1.1;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;                 # SSE
        proxy_read_timeout 3600s;
    }

    location /socket.io/ {
        proxy_pass http://dijiang_api;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
    }

    location / { proxy_pass http://dijiang_web; }
}
```

```bash
sudo certbot certonly --webroot -w /var/www/certbot -d dijiang.example.com
sudo nginx -t && sudo systemctl reload nginx
```

> `proxy_pass http://dijiang_api;` **不要加尾斜杠**，否则 `/api/v1/...` 会被改写丢前缀。

## 21.6 Cloudflare Tunnel 方案（无公网 IP / 不开放端口）

Cloudflare Tunnel 让 `cloudflared` 主动外连 Cloudflare，源站无需公网 IP、无需开 80/443。
HTTPS 由 Cloudflare 边缘终止，源站可以是 HTTP。

### 21.6.1 安装与登录

```bash
# Debian/Ubuntu 示例
curl -fsSL https://pkg.cloudflare.com/cloudflared.repo | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt update && sudo apt install cloudflared

cloudflared tunnel login                 # 浏览器授权，生成 cert.pem
cloudflared tunnel create dijiang        # 生成 UUID + credentials json
cloudflared tunnel route dns dijiang dijiang.example.com
```

### 21.6.2 同源方案（推荐）：源站用本地 Caddy 统一路由

```yaml
# ~/.cloudflared/config.yml
tunnel: <TUNNEL_UUID>
credentials-file: /home/ops/.cloudflared/<TUNNEL_UUID>.json
ingress:
  - hostname: dijiang.example.com
    service: http://127.0.0.1:8080     # 本机 Caddy（同源：web + /api + /socket.io）
  - service: http_status:404
```

```bash
# 本机 Caddy 只监听回环，不暴露公网：
# {$DOMAIN} { bind 127.0.0.1; tls internal; ... } 或用 http://127.0.0.1:8080 的纯 HTTP 站点
caddy run --config ops/Caddyfile
cloudflared tunnel run dijiang
```

浏览器访问 `https://dijiang.example.com`：前端与 API/WS 同源，CORS 只需该 origin；WS 自动支持。

### 21.6.3 两个主机名方案（前端 + API 分开）

```yaml
ingress:
  - hostname: app.example.com
    service: http://127.0.0.1:3100        # Next.js
  - hostname: api.example.com
    service: http://127.0.0.1:3000        # NestJS（/api + /socket.io）
  - hostname: files.example.com
    service: http://127.0.0.1:9000        # MinIO/S3（可选）
  - service: http_status:404
```

此时：
- 前端构建 `NEXT_PUBLIC_API_BASE=https://api.example.com`；
- 后端 `CORS_ORIGINS=https://app.example.com`；
- 两个主机名都走 HTTPS，WS 为 `wss://api.example.com/socket.io`。

### 21.6.4 限制与注意事项

| 限制 | 影响 | 处理 |
| --- | --- | --- |
| Cloudflare 免费版单请求 100MB | 大文件直传经 CF 会被截断 | 文件走 S3 预签名直传而非经 API；若必须经 CF，升级套餐或改走独立域名/直连 |
| CF 会缓冲/改写部分响应 | SSE（`/api/ai/*`）可能延迟 | 源站 `flush_interval -1`/`proxy_buffering off`；确认响应用 `text/event-stream` 且无 `Content-Encoding` |
| WebSocket 由 CF 自动代理 | 需确保 DNS 记录为 Proxied（橙云） | Tunnel 的 route dns 默认已代理 |
| 源站 IP 隐藏 | 直接访问 3000/3100 仍可能绕过 CF | 服务器防火墙只允许 cloudflared 出站；3000/3100 绑 `127.0.0.1` |
| `X-Forwarded-For` 由 CF 设置 | 后端仍要 `TRUST_PROXY=true` | 检查 `/metrics`/审计 IP 是否为真实客户端 |
| `S3_PUBLIC_ENDPOINT` 必须是用户可达的 HTTPS | 预签名 URL 的 host 参与签名 | 用 `files.example.com` 指向 MinIO，且该地址可被浏览器访问；不能是容器内 `minio:9000` |
| CF 对 `Host`/SNI 影响 | 反代需保留 Host | 预签名 host 与浏览器实际访问 host 必须完全一致，否则 `SignatureDoesNotMatch` |

## 21.7 多实例部署

### 21.7.1 前提

- 所有实例连**同一 PostgreSQL、同一 Redis**；S3 桶共享。
- 每个实例 `HOST=0.0.0.0`，监听不同端口或不同容器。
- Redis adapter 已内置（`RedisService.adapterPair()` → `createAdapter`），只要 `REDIS_URL` 有效即启用。
- 每个实例独立连接池：`实例数 × DATABASE_POOL_MAX ≤ PG max_connections`（预留 20% 给运维连接）。

### 21.7.2 Sticky 与 Socket.IO

| 客户端传输 | 无 sticky 多实例 | 有 sticky |
| --- | --- | --- |
| **WebSocket only**（`transports:['websocket']`） | ✅ 可用（握手后连接固定在一个实例） | ✅ |
| 默认（polling → websocket 升级） | ⚠️ 升级前的长轮询请求可能落到不同实例，导致会话/升级失败 | ✅ 推荐 |

结论：
- 前端若配置 Socket.IO 为 `transports:['websocket']`，Redis adapter 足以支撑多实例广播；
- 若保留默认长轮询，**必须**配置会话保持：
  - nginx：`upstream` 加 `ip_hash;`，或按 `$cookie_io` 做 `sticky`（商业模块）；
  - Caddy：`lb_policy cookie`（或外部 LB 的 sticky）；
  - Cloudflare：本身不保证源站会话保持，多实例 + polling 时不稳，建议 websocket-only。

本仓库前端当前使用默认传输（含 polling），因此公网多实例请优先配置 sticky 或改为 websocket-only（需前端改动，本次不改）。

### 21.7.3 健康检查与滚动升级

- 探针：`GET /healthz`（进程存活）、`GET /readyz`（PG + Redis + S3，失败 503）。
- 反代/LB 摘流 → 停旧实例（SIGTERM 优雅退出）→ 起新实例 → `/readyz` 200 后再挂回。
- 数据库迁移先执行（`prisma migrate deploy`），新代码兼容旧 schema 后再滚动；避免旧实例写入新约束失败。
- 注意 WS 连接：滚动时客户端会自动重连（socket.io 重连 + `ready` 后按 lastSeq 补拉）。

## 21.8 常见问题（反代 / CORS / WS / S3）

### 21.8.1 浏览器报 CORS
- 同源部署不应出现 CORS；若出现，说明前端构建的 `NEXT_PUBLIC_API_BASE` 与页面 origin 不同（例如写成了 `:3000`）。
- 分离域名部署：后端 `CORS_ORIGINS` 必须精确包含前端 origin（`https://app.example.com`，无尾斜杠）。

### 21.8.2 WS 一直重连 / 握手 400
- 用浏览器 DevTools 看 `wss://域名/socket.io/?EIO=4&transport=websocket` 是否 101。
- 反代必须转发 `Upgrade`/`Connection`；nginx 用 `$connection_upgrade`，Caddy 默认支持。
- 后端 Ws 的 `allowRequest` 会拒绝不在 `CORS_ORIGINS` 的 Origin，返回 `400 CORS_ORIGIN_NOT_ALLOWED`——把页面域名加入白名单。
- 多实例 + polling 未 sticky：见 §21.7.2。

### 21.8.3 SSE（AI 对话/报告）不流式
- 反代缓冲：Caddy `flush_interval -1`、nginx `proxy_buffering off`；Cloudflare 侧确认未被缓存/压缩策略干扰。
- 确认命中 `/api/*` 路由而不是前端路由。

### 21.8.4 S3 预签名 `SignatureDoesNotMatch`
- `S3_PUBLIC_ENDPOINT` 必须与浏览器实际访问的 **scheme + host + port + path** 完全一致；不能带 `/files` 前缀。
- 反代不要改写 Host（`proxy_set_header Host $host` 保留；MinIO 的 SigV4 校验 host）。
- 不要把 MinIO 挂在 `/files/*` 子路径下（签名 path 会被改写）。

### 21.8.5 客户端 IP 全是 127.0.0.1 / 反代 IP
- 后端 `TRUST_PROXY=true`；Caddy/nginx 设置 `X-Forwarded-For`；Cloudflare 场景确认 CF 传递链。

### 21.8.6 上传 413 / Cloudflare 100MB
- `REQUEST_BODY_LIMIT_MB` 只影响 JSON body；文件应走 S3 预签名直传。
- 经 Cloudflare 的大文件受 100MB 限制，需绕开 CF 或升级套餐。

### 21.8.7 登录态
- 前端使用 **Bearer token + localStorage，无 Cookie**；不存在 SameSite/Domain/Cookie 跨域问题。
- 代价是 token 存在 JS 可读位置：公网部署务必 HTTPS + 强 CSP，避免 XSS。

## 21.9 启动顺序（同源单机）

1. PostgreSQL / Redis / S3 就绪（`/readyz` 依赖）。
2. `prisma migrate deploy`（或 `make migrate`）。
3. 启动 API（`NODE_ENV=production`、`TRUST_PROXY=true`、`REDIS_URL` 必填）。
4. 构建并启动 Web（`NEXT_PUBLIC_API_BASE=https://域名`）。
5. Caddy/nginx 启动并通过 ACME/证书。
6. 验收 §21.10，再开放公网。

## 21.10 验收清单

```bash
# TLS 证书与 HSTS
curl -sI https://dijiang.example.com/ | grep -Ei 'strict-transport|content-security|permissions-policy'

# REST（同源）
curl -s https://dijiang.example.com/healthz
curl -s https://dijiang.example.com/readyz
```
