# 06 · 搜索方案

> 协议编号：O.M.V-DJ / P-06　｜　版本：v1.0　｜　依据：`_contract.md` v1.0 §2.8 `search_vector`、§7 search 端点、§12 验收数据；假设见 `01-目标与缺口.md` A5 / G5。
> 管辖：消息与卡片的检索实现、排序、片段、权限过滤、性能边界与升级触发条件。
> 一句话判据：**PostgreSQL 单库内完成，不引入外部搜索服务**；升级 Meilisearch 需要越过 §8 的阈值。

---

## 1. 中文分词现实

| 方案 | 可行性 | 结论 |
| --- | --- | --- |
| `to_tsvector('zhparser', …)` | 需源码编译 + 词典 + 分词语料，Windows 直装环境无 Docker、无法保证可装 | 不用（`01` 假设 A5 / 缺口 G5） |
| `pg_jieba` | 同上，且词表偏通用语料 | 不用 |
| `to_tsvector('simple', …)` | 内置配置，按标点与空白切分，**不识别中文词边界** | 用，见下 |
| `pg_trgm` | 内置扩展，按字符 3-gram 建索引，中文可工作 | 用，兜底子串 |
| `ILIKE '%x%'` 无索引 | 全表顺序扫描 | 仅用于卡片（数据量小）与短查询回退 |

`simple` 配置不抽词干、不做词典映射，只做小写化与符号切分。中文因此**整段连续汉字会成为一个 token**：

```
to_tsvector('simple', '第三协议的素材归档') = '第三协议的素材归档':1
```

含义：`tsquery` 能精确命中「第三协议的素材归档」这整串，但对「素材」这种子串**零命中**。中文用户的输入恰恰是短词，所以单靠 tsvector 会大面积搜不到。`pg_trgm` 把字符串切成连续 3 字符片段，「素材归档」产生 `素材归`、`材归档`，对「素材」这种 2 字查询仍缺 1 个字符——**2 字查询是最坏情况**，需要降级路径（§3）。

**结论**：双索引不是冗余，是分工。tsvector 保英文 / 数字 / 型号（如 `v2.3`、`DIJIANG-07`）与长中文串的精确检索，trgm 保中文子串的部分召回。

## 2. 索引与字段

| 对象 | 索引 | 服务对象 | 依据 |
| --- | --- | --- | --- |
| `messages.search_vector`（生成列） | `GIN(search_vector)` | `websearch_to_tsquery('simple', q)` | 契约 §2.8 |
| `messages.body` | `GIN(body gin_trgm_ops)` | `body ILIKE '%q%'`、`similarity()` | 契约 §2.8 |
| `messages.mentions` | `GIN(mentions)` | 「我的提及」（属 `07`） | 契约 §2.8 |
| `messages (channel_id, id DESC)` | B-tree | 频道内搜索的范围裁剪 | 契约 §2.8 |
| `cards.title / cards.body` | **无专用索引** | 卡片搜索走频道内顺序扫描 | 契约未建（见 §10 第 1 条） |

`search_vector` 是 `GENERATED ALWAYS AS (to_tsvector('simple', coalesce(body,''))) STORED`：写消息时随行更新，检索时零额外维护开销。`to_tsvector(regconfig, text)` 是 IMMUTABLE，可作生成列；若改用 `to_tsvector(text)` 单参形式（依赖 `default_text_search_config`），生成列会创建失败。

## 3. 查询策略

判定顺序：先判断查询串形态，再决定走哪条索引，最后合并结果。

```ts
type Plan = 'tsquery' | 'trgm' | 'both';

function plan(q: string): Plan {
  const s = q.trim();
  const hasCJK = /[\u4e00-\u9fff]/.test(s);
  const hasLatin = /[a-z0-9]/i.test(s);
  if (hasLatin && !hasCJK) return 'tsquery';        // 英文/数字：词边界清晰
  if (hasCJK && s.length < 3) return 'trgm';        // 中文 1–2 字：trgm 几乎必扫，先限定频道
  if (hasCJK && !hasLatin) return 'trgm';           // 纯中文：子串召回优先
  return 'both';                                    // 混合串
}
```

| 形态 | 主路径 | 说明 |
| --- | --- | --- |
| 纯英文 / 数字（`v2.3`、`DIJIANG`） | `search_vector @@ websearch_to_tsquery('simple', q)` | `websearch_to_tsquery` 天然处理引号、`OR`、`-` 排除，不手拼 tsquery |
| 中文 ≥3 字 | `body ILIKE '%' \|\| q \|\| '%'`（走 trgm） | GIN trigram 对 `ILIKE` 有效；`similarity()` 仅用于排序 |
| 中文 1–2 字 | 同上，但**必须**带 `channel_id` 限定 | 否则 2-gram 覆盖率低，退化为近全表扫描 |
| 混合串 | 两路 UNION，按 id 去重 | 取并集后统一排序 |

**排序与游标**：契约 §3 规定游标为 `base64url("seq:<id>")`，这是 message 的单调序。**排序必须按 `id DESC`**，否则游标无法续页：

| 排序 | 可行性 | 结论 |
| --- | --- | --- |
| `id DESC`（新→旧） | 与契约游标一致，翻页稳定 | **采用** |
| `ts_rank DESC, id DESC` | 需要把 rank 编码进游标，与契约 §3 游标格式冲突 | 不采用（改用「最相关前 20 条」不作为分页路径） |

代价是搜索结果按时间排列而非相关度；对 50 人、30 万条以内的社团空间，「最近说过的」通常就是想要的。

## 4. 权限过滤

### 4.1 全域搜索 `GET /search?q=&channelId=&type=message|card&cursor=`

必须在**同一 SQL** 内完成可见性过滤，不允许「先查再逐条过滤」——后者会泄漏条数。

```sql
-- $1 = userId, $2 = q, $3 = channelId (可为 NULL), $4 = cursorId (可为 NULL)
SELECT m.id, m.channel_id, m.sender_id, m.kind, m.body, m.created_at
FROM messages m
JOIN channel_members cm ON cm.channel_id = m.channel_id AND cm.user_id = $1
WHERE m.deleted_at IS NULL
  AND ($3::uuid IS NULL OR m.channel_id = $3)
  AND ($4::bigint IS NULL OR m.id < $4)
  AND (
        m.search_vector @@ websearch_to_tsquery('simple', $2)
     OR m.body ILIKE '%' || $2 || '%'
      )
ORDER BY m.id DESC
LIMIT 50;
```

`JOIN channel_members` 是权限闸门：私密频道的非成员没有行，天然被排除；owner / admin 也不例外（`05` §4）。公开频道未加入者同样读不到——与契约 §4 矩阵「非成员 ❌」一致。

### 4.2 频道内搜索 `GET /channels/:id/search?q=`

先用 `decide(ctx, 'read')`（`05` §3）判定成员身份，再执行；SQL 多一个 `channel_id = $2`，走 `(channel_id, id DESC)` 索引做范围裁剪，通常只需扫最近几千行。

### 4.3 卡片搜索 `type=card`

```sql
SELECT c.id, c.channel_id, c.kind, c.title, c.body, c.tags
FROM cards c
JOIN channel_members cm ON cm.channel_id = c.channel_id AND cm.user_id = $1
WHERE c.deleted_at IS NULL
  AND ($3::uuid IS NULL OR c.channel_id = $3)
  AND (c.title ILIKE '%' || $2 || '%' OR c.body ILIKE '%' || $2 || '%'
       OR EXISTS (SELECT 1 FROM unnest(c.tags) t WHERE t ILIKE '%' || $2 || '%'))
ORDER BY c.created_at DESC
LIMIT 50;
```

卡片无 trigram 索引，这是**频道内顺序扫描**；按契约 §12 基线（每频道 ≤20 张卡）耗时 < 5 ms，风险见 §10。

## 5. 结果片段

| 语言形态 | 手段 | 输出 |
| --- | --- | --- |
| 英文 / 数字 | `ts_headline('simple', body, websearch_to_tsquery('simple',$2), 'StartSel=<<,StopSel=>>,MaxWords=40,MinWords=15')` | 命中词带 `<<>>` 标记 |
| 中文 | `ts_headline` 对 `simple` 配置无效（整串一个 token），改用应用层切片 | 命中位置 `indexOf` → 前 20 字 + 命中 + 后 30 字，两端加省略号 |
| 卡片 | 仅 `title` + 前 80 字 `body` | 不做标记 |

```ts
function snippet(body: string, q: string, pad = 30): string {
  const i = body.toLowerCase().indexOf(q.toLowerCase());
  if (i < 0) return body.slice(0, pad * 2).trimEnd() + (body.length > pad * 2 ? '…' : '');
  const from = Math.max(0, i - 20);
  const to = Math.min(body.length, i + q.length + pad);
  return `${from > 0 ? '…' : ''}${body.slice(from, i)}<<${body.slice(i, i + q.length)}>>` +
         `${body.slice(i + q.length, to)}${to < body.length ? '…' : ''}`;
}
```

标记符号沿用 `ts_headline` 的 `<<` `>>`，前端只实现一套高亮渲染。

## 6. 性能估算

基线为契约 §12（≥500 条消息、50 人上限）。索引全部在库内，检索不写库。

| 消息量 | 英文 tsquery（p95） | 中文 ≥3 字 trgm（p95） | 中文 2 字（p95） | 备注 |
| --- | --- | --- | --- | --- |
| 500（验收基线） | < 3 ms | < 3 ms | < 5 ms | 任意路径 |
| 5 万 | < 10 ms | 5–15 ms | 15–40 ms | 索引可命中 |
| 30 万（一年预估） | 10–30 ms | 20–60 ms | 60–200 ms（需频道限定） | 2 字查询是拐点 |
| 100 万 | 30–80 ms | 60–150 ms | 不可接受 | 越 §8 阈值 |

三条经验约束：

1. `LIMIT 50` 且 `ORDER BY id DESC` 时，PG 可走索引后停止；一旦带 `OR` 的混合查询，必须确保两端都能各自走索引，否则退化为位图并集 + 排序。
2. 中文 1–2 字查询**必须**带 `channelId`，否则 `pg_trgm` 的选择率不足，实际执行会变成全表扫描（`EXPLAIN` 显示 `Seq Scan` 即判定失败）。
3. 片段生成在应用层做，不放进 SQL：`ts_headline` 对中文无效，对英文也只取一次，避免每行昂贵计算。

## 7. 何时升级 Meilisearch

触发条件为**或**关系，任一满足即启动迁移评估：

| # | 指标 | 阈值 | 判定方式 |
| --- | --- | --- | --- |
| 1 | `messages` 行数 | > 30 万 | `SELECT count(*)` |
| 2 | 搜索 p95 | 连续 7 天 > 300 ms | `09` 的 `http_request_duration_ms{route="/search"}` |
| 3 | 卡片搜索占比 | `type=card` 请求 > 全部搜索的 30 % | 访问日志聚合 |
| 4 | 2 字中文查询占比 | > 40 % 且 p95 > 150 ms | 查询串长度分布直方图 |
| 5 | 搜索 QPS | 峰值 > 5 req/s 且 CPU > 70 % | Prometheus |
| 6 | 新需求 | 需要拼音、前缀补全、错字容错、多语言 | 产品判断 |
| 7 | 用户数 | > 100（见 `10` §6 的 P2） | 部署阶段 |

迁移路径（不改 API 形状，只换实现）：

1. 建 `search_outbox`（写消息时同事务插一条），由 Worker 投递到 Meilisearch；PG 仍是唯一事实源。
2. 首次全量导入 + 增量双写，检索读走 Meilisearch，`/search` 响应结构不变（`id / channelId / snippet / createdAt`）。
3. 权限过滤仍在应用层拼 `channelIds` 白名单（Meilisearch 的 filter 只做 `channel_id IN [...]`），不把权限逻辑下推到外部引擎。
4. 灰度：按 `userId % 10` 分流，PG 路径保留一个版本周期作回滚。

不迁移的信号：查询几乎都是「找最近说过的某句」，且 `messages < 30 万`——此时外部引擎带来的运维面（多一个进程、多一套索引一致性、多一份磁盘）大于收益。

## 8. 取舍记录

| 议题 | 采用 | 理由（一句） | 备选与代价 |
| --- | --- | --- | --- |
| 检索引擎 | PostgreSQL 内双索引 | 零新增服务，权限过滤与业务表同库同事务 | Meilisearch / ES：召回与排序更好，但引入第二份数据与同步一致性 |
| 中文分词 | `simple` + `pg_trgm` | 无需编译词典，Windows 直装可复现 | zhparser：分词质量高，但依赖源码编译与词典维护 |
| 检索字段 | 仅 `body`（消息）/ `title+body`（卡片） | 与「搜得到看得懂」一致 | 加入 `original_name`（附件名）：噪声大，需额外索引 |
| 排序 | `id DESC` 固定 | 与契约游标格式兼容，翻页稳定 | 相关度排序：需要复合游标，与契约 §3 冲突 |
| 片段 | `ts_headline` + 应用层切片 | 一套标记，前端一个渲染器 | 纯 SQL 高亮：中文失效；纯前端高亮：要传全文 |
| 权限过滤 | SQL 内 JOIN 成员表 | 一条查询出结果，不泄漏条数 | 应用层过滤：简单但先取后删，条数与时延都失真 |
| 索引维护 | 生成列 | 写入即一致，无需补偿任务 | 触发器 / 异步重建：多一条可能失败的路径 |

## 9. 已识别薄弱点

1. **卡片搜索无索引**：契约只为 `messages` 定义了 trigram 与 tsvector 索引，`cards` 没有。当前靠「每频道 ≤20 张卡」的顺序扫描兜底；一旦卡片数量上去（或多频道聚合搜索），`type=card` 会成为最慢路径。建议 v1.1 为 `cards.title`、`cards.body` 补 trigram 索引。
2. **2 字中文查询是硬伤**：trigram 需要 3 字符才能形成完整片段，2 字查询在 30 万条时 p95 可达 200 ms 且依赖频道限定；这是不引入分词器的直接代价。
3. **无拼音与错字容错**：「sucai」搜不到「素材」，写错一个字也搜不到；在中文语境下这是可用性缺口，只能靠 §7 阈值 6 触发升级。
