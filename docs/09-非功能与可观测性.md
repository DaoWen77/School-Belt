# 09 · 非功能需求与可观测性

> 协议编号：O.M.V-DJ / P-09　｜　版本：v1.0
> 一句话：把「快、不丢、不重、扛得住 50 人」写成可测量、可告警、可复盘的指标。

## 1. SLO 与测量口径

| # | 指标 | 目标 | 测量点 | 统计窗口 |
| --- | --- | --- | --- | --- |
| S1 | 消息端到端 P95 | **< 300 ms** | 发送端 `send()` 调用 → 接收端 `message:new` 渲染；同城网络 | 5 min 滚动 |
| S2 | 发送 ack P95 | < 150 ms | 服务端收到帧 → 持久化完成并回 ack | 5 min 滚动 |
| S3 | 断线重连 P95 | **< 5 s** | socket `disconnect` → 重新 `ready` 并补齐消息 | 单次事件 |
| S4 | REST P95 | < 200 ms | 网关入口 → 响应头 | 5 min 滚动 |
| S5 | 搜索 P95 | < 400 ms | 请求 → 结果 | 5 min 滚动 |
| S6 | 预签名 P95 | < 80 ms | 请求 → URL 返回 | 5 min 滚动 |
| S7 | 月可用性 | 99.5%（单机） | `/healthz` 探活 + 外部拨测 1 min | 30 天 |
| S8 | 消息持久化成功率 | ≥ 99.99% | ack 成功 / 发送尝试（不含客户端校验失败） | 30 天 |
| S9 | 推送到达率 | ≥ 95% | push provider 回执 sent / 应推 | 7 天 |
| S10 | 数据 RPO / RTO | 24 h / 4 h | 备份成功时间 / 恢复演练耗时 | 季度演练 |

> S1 的 300 ms 是**端到端**；其中 S2 占大头，广播（Redis → 各实例 → 客户端）预算 150 ms。50 人同频道广播量 ≤ 50 帧/条消息，单实例写 50 个 socket 约 1–3 ms，余量充足。

### 1.1 预算分解（P95，单条消息）

| 阶段 | 预算 |
| --- | --- |
| 网络入站（客户端 → API） | 40 ms |
| 鉴权 + 校验 + 权限查询（Redis 缓存命中） | 15 ms |
| PG 事务写入（messages + 附件 + 未读） | 25 ms |
| 事务后广播（Redis publish + 本机 emit） | 35 ms |
| 网络出站（API → 接收端） | 40 ms |
| 客户端渲染 | ≤ 100 ms（前端预算，计入 S1） |
| **合计** | **≈ 255 ms** |

## 2. 不丢不重

### 2.1 不丢

1. **先持久化后 ack**：WS `message:send` 只有在 PG 事务提交后才回 ack；ack 前的任何失败，客户端视为未发送。
2. **客户端重试**：ack 超时 5 s → 用同一 `clientMsgId` 重发，指数退避 1/2/4/8 s，最多 5 次；仍失败则落本地草稿箱并提示。
3. **补拉兜底**：任何重连（`ready` 后）都执行一次 `GET /channels/:id/messages?direction=newer&cursor=lastSeq`，补齐断线窗口。广播失败不会导致丢消息，只会导致「晚到」。
4. **进程崩溃**：PG 事务保证已提交即存在；未提交的发送不会有 ack，客户端会重试。

> 结论：投递语义是 **at-least-once + 客户端按 message.id 去重**。这是 50 人规模下成本最低、最容易验证的方案；真正的 exactly-once 需要分布式事务，收益不抵成本。

### 2.2 不重

1. **幂等键**：`clientMsgId`（UUID v4，客户端生成），落库唯一约束 `UNIQUE(channel_id, sender_id, client_msg_id)`。
2. **冲突处理**：捕获唯一键冲突（PG `23505`）→ 查出已存消息 → ack 返回 `{ ok: true, dup: true, message }`；不重复广播。
3. **客户端去重**：按 `message.id` 维护已渲染集合；补拉与实时推送可能同时到达同一条，丢弃重复。
4. **重复发送的边界**：同一用户在不同频道用同一 `clientMsgId` 允许（唯一键含 channel_id）；这是有意的，避免跨频道客户端复用时误判。

### 2.3 重连状态机

```
CONNECTING --失败--> BACKOFF(1s,2s,4s,8s,16s 封顶) --成功--> AUTH
AUTH --ready--> SYNCING --补拉完成--> LIVE
LIVE --disconnect--> BACKOFF
SYNCING --失败--> BACKOFF（保留 cursor，不丢）
```
- 重连时携带 `lastSeq`（客户端已渲染最大 id），服务端不需要状态，补拉接口按 cursor 返回。
- 页面从后台恢复（`visibilitychange`）时主动探活：`presence:ping` 超时 2 s 则重建连接。

## 3. 限流

| 维度 | 规则 | 实现 |
| --- | --- | --- |
| 登录 | 5 次/分钟/IP；10 次/小时/账号 | Redis 滑动窗口 |
| 注册（邀请核验） | 5 次/10 分钟/IP | Redis 计数 |
| 发消息 | 令牌桶：5/s 突发，60/分钟 | Redis + Lua，key `rl:msg:{userId}` |
| 上传签名 | 20/分钟/用户 | 同上 |
| 搜索 | 10/分钟/用户 | 同上 |
| WS 连接 | 10 次/分钟/IP | 握手阶段拒绝 |
| 已读上报 | 客户端 500 ms 节流；服务端 300 ms 合并 | 内存 Map + 定时 flush |

超出返回 `429 RATE_LIMITED` 并带 `retryAfterMs`；WS 场景回 ack 错误，不主动断开（除握手）。

## 4. 日志

- 结构化 JSON（pino），stdout 输出，由 Docker `json-file`（max 20MB×5）或 Loki 收集。
- 每条请求日志字段：`ts, level, requestId, userId, route, method, status, durMs, ip, ua, errCode`。
- WS 日志：`event, userId, channelId, messageId, clientMsgId, dup, durMs`。
- **脱敏**：密码、token、邀请码、S3 签名 URL、消息正文默认不进日志（正文只记录长度与 id）；`authorization` 头打码。
- 级别：生产 `info`，错误 `error`；调试用 `LOG_LEVEL=debug` 临时开。
- 保留：应用日志 14 天；审计日志（audit_logs）1 年。

## 7. 备份与恢复

| 项 | 策略 |

## 8. 安全基线

1. 全站 HTTPS（Caddy 自动证书），HSTS 365 天（`max-age=31536000; includeSubDomains`）；WS 只走 `wss`。
2. CORS 白名单（`WEB_ORIGIN`），禁止 `*` 携带凭证。
3. 密码 argon2id（m=19456, t=2, p=1）；登录失败不区分账号不存在/密码错。
4. JWT：access 15 min（HS256，`JWT_SECRET` ≥ 32 字节），refresh 30 天且**每次轮换**，旧 refresh 立即失效（重放检测：检测到已轮换 token 再次使用 → 吊销整条链）。
5. 邀请码只存 sha256，明文仅创建时返回一次；错误统一 `INVITE_INVALID`。
6. 上传：签名时固定 `Content-Type` + `content-length-range`；完成后 HEAD 校验大小、读前 512 字节魔数；SVG 一律转 PNG 预览或拒绝；压缩包不解析。
7. S3 桶私有，所有读取走 15 分钟签名 URL；禁止列出桶。
8. 安全响应头：CSP（`default-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:`）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`、`Permissions-Policy` 关闭不需要的能力。
9. WS 消息体大小上限 64 KB；单条消息附件 ≤ 10。
10. 依赖：`pnpm audit` 纳入 CI；Dependabot 周更。
11. 预留：可选 ClamAV 扫描（`VIRUS_SCAN_ENABLED=false` 默认关）。

## 9. 容量估算（50 人）

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 日活消息 | 50 人 × 80 条 = 4,000 条/日 | 重度创作社团上限 |
| 单条存储 | 正文 ~300 B + 索引 ~200 B | 约 0.5 KB |
| 消息年增 | 4,000 × 365 × 0.5 KB ≈ 0.7 GB | 可忽略 |
| 文件 | 50 人 × 每周 20 个 × 5 MB ≈ 5 GB/周 | 主要成本；按 200 GB 磁盘可用 8 个月 |
| 峰值并发连接 | 50 × 1.5（多标签）= 75 | 单实例轻松承载 |
| 峰值广播 | 1 条 × 50 接收 × 3 事件 | < 5,000 帧/分钟 |
| Redis 内存 | presence 75 key + 限流 key ≈ 20 MB | 256 MB 足够 |
| PG 连接 | api 10 + worker 2 | PgBouncer 可选 |

## 10. 压测方案（50 并发）

工具：k6（HTTP + WebSocket）。脚本放 `ops/loadtest/k6-chat.js`，CI 手动触发。

```js
import ws from 'k6/ws';
import { check } from 'k6';
export const options = { vus: 50, duration: '2m', thresholds: { checks: ['rate>0.99'] } };
export default function () {
  const token = __ENV.TOKEN;                       // 预置 50 个测试账号
  const url = `wss://${__ENV.HOST}/ws?EIO=4&transport=websocket`;
  const res = ws.connect(url, { headers: { Authorization: `Bearer ${token}` } }, (socket) => {
    socket.on('open', () => socket.send('40'));     // Socket.IO connect
    let sent = 0;
    socket.setInterval(() => {
      const id = `${__VU}-${Date.now()}-${sent++}`;
      socket.send(`42["message:send",{"channelId":"${__ENV.CHANNEL}","clientMsgId":"${id}","kind":"text","body":"load ${id}"}]`);
    }, 1000);
    socket.setTimeout(() => socket.close(), 30000);
  });
  check(res, { 'status 101': (r) => r && r.status === 101 });
}
```

验收口径：50 VU 持续 2 分钟，S1 P95 < 300 ms、S2 P95 < 150 ms、零 `ack_timeout`、零重复。

## 11. 可观测性栈（最小）

| 组件 | 单机方案 | 说明 |
| --- | --- | --- |
| 指标 | Prometheus + Grafana | 或 Uptime Kuma + 自建 `/metrics` 抓取 |
| 日志 | Loki + Promtail | 或 `docker logs` + 每日归档 |
| 追踪 | OpenTelemetry（可选，默认关） | 50 人规模收益有限 |
| 拨测 | 外部 HTTP 探活 1 分钟 | `/healthz` + 一次登录态查询 |

> 取舍：50 人规模不值得上全套 SRE 栈；优先保证「能定位一条消息为什么慢」——requestId 贯穿日志 + 三个直方图足够。备选：托管 Sentry 做异常聚合。
